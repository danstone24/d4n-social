SocialApp: plan and mocks

Working title. An iPhone app that opens Instagram and X inside its own browser and strips the parts we do not want. 30 Sep 2026, draft 2 (built 1 Oct: shell A, all recommendations approved).

The apps you are thinking of (Dull, UNDOOMED, SocialLite, ScrollGuard) all do the same thing: load the platform's mobile website in a WebView, inject CSS and JavaScript to hide Reels, Explore, ads and suggestions, and block a few URLs natively. That is the TwitterCleanser model with a native shell around it. Everything below assumes that approach. The open decisions are in the chat round that goes with this document.

2. How it works

Native shell (SwiftUI)Same skeleton as CellSignal: XcodeGen project.yml, scripts/sim.sh, scripts/testflight.sh, bundle prefix uk.d4n. Holds one WKWebView per platform, a settings store, and the filter settings screen. The D4N Travel web shell (WebTab.swift) is the starting point for the WebView owner.
settings flags down, hidden counts up
WKWebView per platformLoads instagram.com or x.com. Persistent cookie store so login sticks between launches. User agent ends in Mobile/15E148 Safari/604.1 so the sites treat it as Mobile Safari, not an in-app browser. Inline media playback on. Native navigation policy denies /reels/, /explore/ (except search), instagram:// and App Store bounces before they load.
WKUserScript at document start
Rules: content.js + cleanser.css per platformLifted from TwitterCleanser. JS marks unwanted elements with data-tc-*, CSS hides them, gated on flags on <html>. Toggling a filter off removes the flag and everything comes back with no reload. MutationObserver with a debounced rescan handles infinite scroll. The only change is the settings transport: storage.sync becomes a native bridge (window.webkit.messageHandlers in, evaluateJavaScript out).

What this means in practice: the X rules are mostly a port, with a pass for the mobile layout. The Instagram rules are new, but the shape is identical and Glance shows the selectors that work. Neither site is modified or reverse engineered beyond what the browser already sees.

4. Instagram: proposed rule set for v1

Hidden by default

  • Reels tab in the bottom bar, and the /reels/ route natively
  • Reels and suggested posts in the home feed ("Suggested for you", "Reels" carousels)
  • Explore grid (/explore/); search stays
  • Ads ("Sponsored" label)
  • Suggested accounts carousels in feed and on profiles
  • "Open in app", "Use the app" and App Store banners
  • Threads promotion and Meta AI entry points
  • Shopping tab and product tags

Off by default, toggleable

  • Stories row
  • Like and view counts
  • Comments under posts
  • Notifications tab
  • DM-only mode (feed hidden, opens on inbox)
  • Stop at "You're all caught up" (no further loading)
  • Following feed only (drop the For You tab)

Always kept

  • Home feed from people you follow, profiles, single posts, DMs, posting photos, search for people

5. Known limits of the wrapper model

  • No push notifications. The web versions cannot deliver them into a WebView. Every wrapper app lists this as its top complaint. The usual answer is to keep the native app installed for pushes only, or accept none.
  • Instagram web cannot upload video to posts or stories. Photos post fine.
  • Login happens inside the WebView with the normal form. 2FA works. "Continue with Facebook" does not, because the Facebook cookie is not shared. Instagram sometimes expires web sessions and asks you to log in again.
  • Both sites change their DOM. X does it often. Text matching is English only. That is what audit mode and quick rule updates are for.
  • Slower than native. Feeds render in WebKit. Video plays inline but the experience is web, not the app.
  • Apple review is not a concern while this ships through TestFlight like CellSignal. It would be if it went to the App Store (wrapper apps get rejected under guideline 4.2).

8. Ideas worth a decision

  • Rules over the air. Bundle the rules in the app, but also fetch rules/x/content.js and friends from the repo's main branch on launch and cache them. A selector fix is then a git push, not a TestFlight build and ten minutes of processing. The bundled copy is the fallback if the fetch fails.
  • One rule source with TwitterCleanser. The extension's content.js and cleanser.css could move into this repo and the extension could load them from here, with a thin adapter for storage. One fix, both places. The cost is coupling two projects and the mobile layout still needs its own selectors. The safe start is to copy the logic in and unify later if the drift hurts.
  • Deep-link quick actions. Home screen quick actions and a widget that open straight to Instagram DMs or X notifications, so the feed is opt-in rather than the default landing.
  • DM-only mode with a schedule. Feed hidden during work hours, back in the evening. Cheap to add once flags are native.
  • Hidden counters. Free, since the rules already count marks. A small "412 hidden this week" line is a good reminder of why the app exists.
  • Post-level swipe to block. The extension's ⃠ button already works on mobile; a swipe gesture on the native side could trigger the same API call with an undo toast.

9. Facts checked

  • Xcode 26.6 and XcodeGen 2.46 are installed on the Mac mini. iPhone 17 Pro simulators exist, including the one CellSignal's sim.sh uses.
  • CellSignal targets iOS 18, D4N Travel iOS 17. Both are iPhone only, bundle prefix uk.d4n, team FFT4Y887VQ, TestFlight via the App Store Connect key.
  • D4N Travel's WebTab.swift already covers WKWebView ownership, user agent token, external link policy, script message bridging and error states.
  • Glance (open source Swift wrapper) documents the Instagram selectors, the Mobile Safari user agent suffix, and a native URL blocklist. It has no licence file, so the approach is borrowed and the code is written fresh.
  • Instagram and X mobile web both work logged in inside WKWebView with a persistent data store. Notifications do not.
